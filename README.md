# design-knowledge

Дизайн-система как знание, которое лежит в git и которым может пользоваться любой агент.

Обычно дизайн-система знает, **из чего** собирать интерфейс: компоненты и токены. Здесь она знает ещё и **зачем**: какие проблемы пользователя решает редизайн и какими паттернами эта система предпочитает их решать. Агент получает не библиотеку кнопок, а цепочку, по которой можно проверить каждое решение:

```
проблема P-001 «не могу прикинуть, потяну ли дом»
   │  tags ↔ solves
паттерн price-anchor          силы: прозрачность бюджета против «не каталог дешёвых домов»
   │  uses, composition
компоненты project-card, price-range, button  →  токены
   │
решение D-004                 почему так, что предполагаем, что спросить у клиента
```

## Слои

| Слой | Что знает | Формат |
|---|---|---|
| `invariants/` | Сущность компании, которую редизайн не трогает | YAML |
| `problems/` | Что не так, у кого и как это видно, на формальном «языке описания проблем» | `schema/problem.schema.yaml` |
| `patterns/` | Как эта система предпочитает решать такие проблемы: условия, силы, связи с другими паттернами | `schema/pattern.md` |
| `composition/` | Способы компоновки: сетка, ритм, иерархия | Markdown |
| `components/`, `tokens/` | Из чего собирается решение | YAML, DTCG |
| `decisions/` | След каждого решения: какая проблема, какой паттерн, почему | `schema/decision.md` |

Проблемы и паттерны связаны через общий словарь тегов `tags.yaml`, а не через номера. Проблемы принадлежат проекту, а паттерн переживает проект и переезжает в следующий.

Формат паттерна взят у Кристофера Александера («A Pattern Language», 1977): контекст, проблема, силы, решение, связи. Главное поле это `forces`, конфликт, который паттерн разрешает. Если конфликта нет, паттерн не нужен, хватит правила в `composition/`.

Ничего не привязано ни к Figma, ни к конкретному AI-продукту. Любой агент читает `AGENTS.md` и работает по тем же правилам.

## Как начать свой проект

```
cp -r template my-project
pip install pyyaml
python3 scripts/check.py my-project
```

Дальше: заполнить `invariants/`, выписать проблемы, завести паттерны под их теги, дать агенту `AGENTS.md` и папку проекта.

`scripts/check.py` проверяет связность графа: у каждой открытой проблемы есть паттерн, паттерны ссылаются на существующие компоненты и друг на друга, компоненты используют существующие токены, решения ссылаются на реальные проблемы и паттерны и закрывают их теги, непроверенные допущения не дают принять решение.

## Пример: редизайн главной Главподряда

`examples/glavpodryad/` это реальный проект: концепт редизайна главной glavpodryad.pro, строительство загородных домов в Ростовской области. Показывается с согласия компании.

Внутри всё знание о редизайне (5 проблем, 5 паттернов, решения), макеты компонентов в `design/` и статическая главная по эталону в `site/`.

```
python3 scripts/check.py examples/glavpodryad
python3 examples/glavpodryad/check_site.py
```
