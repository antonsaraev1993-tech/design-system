# AGENTS.md

Точка входа для любого агента (Claude, Codex, Cursor, свой скрипт). Знание о проекте лежит в его папке, внешний контекст не нужен.

Проект это папка с файлом `tags.yaml`: `examples/glavpodryad/` или твоя копия `template/`. Ниже пути даны от папки проекта, форматы лежат в `schema/` в корне репозитория.

## Что в папке проекта

| Папка | Что это | Можно ли менять агенту |
|---|---|---|
| `invariants/` | Сущность бренда: то, что редизайн не меняет | Нет. Только читать |
| `problems/` | Проблемы на формальном языке (`schema/problem.schema.yaml`) | Нет. Предлагать новые через `status: proposed` |
| `patterns/` | Предпочитаемые паттерны, формат `schema/pattern.md` | Нет. Предлагать новые через `status: proposed` |
| `composition/` | Правила компоновки: сетка, ритм, иерархия | Нет |
| `components/` | Каталог компонентов. Это единственный источник компонентов: если в макете или коде есть компонент, которого здесь нет, считай, что его нет | Нет |
| `tokens/` | Токены в формате DTCG | Нет |
| `tags.yaml` | Словарь тегов, общий для проблем и паттернов | Нет |
| `decisions/` | Решения: какая проблема каким паттерном закрыта и почему | Да, это твой основной выход |

Всё остальное (макеты, код сайта, скриншоты) это материал, а не знание. Читать можно, ссылаться в решении только на то, что есть в таблице.

## Порядок работы

1. Прочитай `invariants/`. Всё, что там есть, ограничивает любое решение.
2. Возьми проблему из `problems/` со `status: open`. Поле `baseline` говорит, по какой версии страницы она описана.
3. Найди паттерн, у которого `solves` пересекается с `tags` проблемы. Проверь `when` и `avoid_when`.
4. Условие, которое нельзя проверить по репозиторию, не считается ни выполненным, ни нарушенным. Решение можно написать, но со `status: draft` и с этим условием в `assumptions` (что предполагаем, какое поле паттерна, что будет, если неверно). Решение с непроверенными `assumptions` не может быть `accepted`.
5. Прочитай `forces` паттерна. Если правило из тела паттерна спорит с силой, побеждает сила, а противоречие запиши в открытые вопросы.
6. Пройди по `related.contains`: эти паттерны входят в решение и указываются в шапке.
7. Если подходящего паттерна нет, не придумывай решение молча. Создай черновик паттерна со `status: proposed` и укажи это в решении.
8. Собери решение только из компонентов `components/index.yaml` и правил `composition/`. Новые цвета, отступы, шрифты запрещены: только токены.
9. Закрой основной тег проблемы (первый в `tags`). По остальным тегам явно напиши в разделе «Теги проблемы», закрыты ли они и где.
10. Запиши решение в `decisions/` по шаблону `schema/decision.md`.
11. Запусти `python3 scripts/check.py <папка проекта>`. Решение без зелёной проверки не считается готовым.

## Чего не делать

- Не менять позиционирование, тон и фирменные элементы из `invariants/`.
- Не ссылаться на паттерны и компоненты, которых нет в папке проекта.
- Не переписывать описания проблем под удобное решение.
- Пометки вида `[уточнить у клиента]` означают, что факта пока нет. Не заполняй их догадками.
